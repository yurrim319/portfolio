## 개요 (Overview)

 **VV World**는 고가의 모션캡처 슈트나 전문 스튜디오 장비 없이도 언리얼 엔진 기반의 고품질 콘텐츠를 손쉽게 제작할 수 있는 **버추얼 콘텐츠 제작 애플리케이션**이다. 게임 엔진 지식이 전혀 없는 사용자도 언리얼 엔진 수준의 시네마틱 퀄리티로 실시간 스트리밍을 할 수 있도록 지원하는 것이 핵심 가치이며, 기존 유니티 기반 타사 툴과 차별화되는 지점이다.

 약 스무명의 기존 버추얼 스트리밍 크리에이터를 대상으로 신규 서비스에 대한 요구사항을 설문 조사한 결과, **캐릭터가 매력적으로 보이는 룩뎁**(50%)이 가장 높은 비중을 차지했고, 이어서 저비용 고퀄리티 모션캡처 솔루션(20%), 커스터마이징 가능한 배경(10%), 게임 스트리밍과 병행 가능한 수준의 최적화(10%) 순으로 나타났다.

 이를 바탕으로, 기존 콘텐츠 제작에서 검증된 **고품질 리소스를 프리셋화·최적화**하여 **실시간 스트리밍 환경에서도 시네마틱 퀄리티**를 구현하는 것을 목표로 설정했다.

 이 목표를 달성하기 위해 Global Light, World Control, Post Process, Camera 등의 기능을 신규 제작하거나 기존 기능을 개선했다.

## 문제 정의 (Problem) - 해결 (Solve)

#### **① Global Light — FLinearColor Replication 버그 (Save Scene 로드 시)**

**▶ 문제상황**

 Blueprint로 만들었던 클래스를 C++로 리팩토링한 뒤, Save Scene을 불러올 때 컬러 값(FLinearColor)이 일부만 반영되고 나머지는 이전 값 그대로 남는 문제가 발생했다. Save Scene 로드 과정은 `Preload → Load → Apply Preset → Post Load` 4단계로 구성돼 있고, Load 단계에서 FLinearColor 변수를 기본값(Default)으로 캐싱하는 처리를 넣었다.


**▶ 원인파악**

 디버깅 결과, 다음 Apply Preset 단계가 원인이었다. 이 단계는 "Save 데이터 값과 Default 데이터 값이 같으면 다시 전송하지 않는" 최적화 로직을 갖고 있었는데, 이 비교가 구조체 전체 단위가 아니라 구조체 안의 개별 필드(R/G/B/A) 단위로 이루어지고 있었다. 

 그래서 R/G/B/A 중 하나라도 Save 값과 Default 값이 우연히 같으면 그 필드는 "변경 없음"으로 판단해 서버로 전달되지 않았고, 캐싱 이전 값이 그대로 남아 컬러가 부분적으로 틀어졌다. (`DOREPLIFETIME` 자체의 설정 문제가 아니라, 그 위에서 도는 값 비교 로직을 우회해야 하는 상황이었다.)


**▶ 해결**

 서버 분기(server branch)에서만 동작하는 함수를 만들어, Apply Preset 시점에 현재 데이터를 Default 데이터로 구조체 전체 단위로 강제 재할당하도록 처리했다.





#### **② Global Light / LookDev Controller — 캐릭터·배경 라이팅 분리 (라이트 채널)**



**▶ 문제상황**

 아트팀 요청으로, 배경(env)은 PBR 기반, 캐릭터는 PBR과 툰쉐이더를 혼용하는 상황에서 두 렌더링 방식 모두에서 캐릭터 라이팅(룩뎁)을 배경과 독립적으로 예쁘게 제어할 수 있어야 했다.



**▶ 원인파악**

 캐릭터와 배경 라이팅이 하나의 라이트 세트를 공유하고 있어, 캐릭터 쪽만 따로 조정하면 배경도 함께 바뀌어 분리 제어가 불가능한 구조였다. 분리 방법으로 Scene Capture(별도 카메라로 렌더링 후 합성)도 검토했으나 두 가지 이유로 기각했다. 

 첫째, Scene Capture는 렌더링을 한 번 더 도는 구조라 비용이 크고, 이미 에디터용/방송 송출용으로 두 개를 쓰고 있어(현재 View Family 통합으로 최적화 진행 중) 여기에 하나를 더 얹기 어려웠다. 

 둘째, 이 작업 자체가 아트팀 요청이 컸기 때문에 아트팀이 직관적으로 다룰 수 있는 방식이어야 했는데, 복잡한 렌더 파이프라인보다는 라이트 하나에 채널 번호만 지정하면 되는 Light Channel 방식이 아트팀 입장에서 바로 납득할 수 있는 선택이었다.



**▶ 해결**

 Global Light(배경)는 채널 0, VVLookDevController(캐릭터 전용 Directional Light 1개)는 채널 2로 완전히 분리하고, Sky Light처럼 GI(전역 조명)처럼 보이는 요소만 0/2 채널을 혼용해 배경과 캐릭터가 자연스럽게 어우러지도록 했다.

 추가로 Forward Shading Proxy 우선순위 문제도 함께 해결해야 했다. 언리얼에서 Water, Fog 같은 일부 머티리얼은 Forward Shading 방식으로 처리되는데, 이 방식은 여러 라이트 중 우선순위(Priority)가 가장 높은 라이트 하나만 골라 연산한다. 낮/밤에 따라 활성 라이트가 서로 교체되는 구조였기 때문에, "지금 켜진 라이트가 항상 1순위가 되도록" Priority 값을 코드에서 동적으로 갱신하는 처리를 추가했다. 이 처리가 없으면 라이트가 바뀌어도 Water/Fog 같은 머티리얼은 이전 라이트 기준으로 렌더링되는 불일치가 생긴다.

 `IsDay` 플래그를 MPC 파라미터로 아트팀에 노출해, 낮/밤 전환 시 배경 아트가 자동으로 반응할 수 있게 했다.





#### **③ PostProcess — 내장 기능의 커스터마이징 한계**



**▶ 문제상황**

 언리얼 내장 PostProcess의 LUT 등은 intensity 같은 수치 조절만 가능하고 개별 스탯을 켜고 끄는 세밀한 제어는 불가능했다. 아트팀은 기존 시네마틱 제작에서 쓰던 기능을 스트리밍 환경에서도 "정확히 그대로" 쓰고 싶어했다.



**▶ 원인파악**

 내장 기능을 그대로 쓰면 커스터마이징 폭이 좁아 아트팀의 기존 워크플로우를 포기해야 하는 트레이드오프가 있었다. 초기에는 커스텀 엔진 소스에 Enable 플래그를 직접 추가하는 방식을 검토했으나 기각했다. 이유는 두 가지다. 

첫째, 오픈 베타 직전이라 빌드 일정이 촉박했고, 커스텀 엔진을 수정하면 다른 개발자들의 빌드/작업 시간에도 영향이 가는 상황이었다. 

둘째, 이미 PostProcess Material을 쓰는 코드 구조가 마련돼 있어서 굳이 엔진 코드를 건드릴 필요 자체가 없었다.


**▶ 해결**

언리얼 엔진 소스에서 LUT 샘플링 로직을 직접 분석해, 동일한 로직을 Material Editor에서 PP Material 함수로 그대로 재현했다. 엔진을 건드리지 않고도 아트팀이 원하는 세밀한 on/off 제어를 구현했고, 최적화를 위해 여러 기능을 각각 별도 머티리얼로 만들지 않고 하나의 PP Material 안에 함수(function) 형태로 모아 넣어 GPU 부하도 줄였다. 그 결과 Filter 8종, 2D Rim Light 옵션 2종을 유저 제어 요소로 제공할 수 있었다.

## 구현 (Implementation)

#### **- Global Light**

 50종 이상의 배경에 대해 언리얼 엔진 환경 라이팅을 프리셋 형태로 구성했다. Directional Light 2개(낮/밤), Sky Light, Atmosphere Sky, Exponential Fog, Volumetric Cloud, Sky Sphere Mesh, HDRI Dome을 하나의 클래스 안에서 컴포넌트로 세팅할 수 있도록 제작해, 수작업 8단계로 진행하던 세팅 과정을 1단계로 축소했다.

 아뽀키 등 기존 콘텐츠 제작팀에서 사용하던 라이팅 프리셋을 최대한 그대로 계승할 수 있도록 하나의 세팅 클래스로 통합했으며, 이를 통해 배경당 약 2시간이 소요되던 작업 시간을 30분 내외로 단축했다.

 툰 셰이더의 밝기에 맞춰 Exposure 등을 자동 조정해 캐릭터 라이팅과 배경이 아트적으로 조화를 이루도록 하되, 사용자가 세부적으로 커스터마이징할 수 있는 여지를 남겨두었다. "기본값만으로도 만족스러운 비주얼이 나오는 것"을 목표로 설계했다

 특히 낮/밤 시간대 변화에 따라 배경 머티리얼이 자동으로 전환되도록, 아트팀과 협의해 Material Parameter Collection(MPC) 구조로 파라미터를 전달하는 방식을 설계했다 (판단 근거는 기술적 챌린지 참고)



#### **- World Control**

 아트팀이 사전 배치한 월드 내 에셋을 사용자가 직접 커스터마이징할 수 있도록, 각 에셋을 C++ 클래스로 래핑하고 공통 UInterface로 연결했다. 아트팀이 직접 세팅할 수 있도록 이 UInterface를 상속받는 Blueprint Interface를 함께 제공해, 에디터 상에서 기존 블루프린트 클래스들과도 자연스럽게 대응되도록 구성했다 (판단 근거는 기술적 챌린지 참고)

 이를 통해 배경 요소별로 개별 구현을 반복하지 않고 World Control이라는 단일 시스템으로 통합 제어할 수 있도록 했다. 레벨당 최대 6개 요소를 컨트롤할 수 있으며 요소별 에셋 개수는 가변적으로 세팅 가능하다. 대형 레벨처럼 제어 대상 에셋 수가 많고 가변적인 경우, 에셋 각각의 참조를 들고 개별 호출하는 대신 MPC 전역 변수를 브로드캐스트해 다수의 에셋이 동시에 같은 상태를 반영하도록 처리했다 (판단 근거는 기술적 챌린지 참고)



#### **- PostProcess**

 화면 룩을 결정하는 기능을 목적에 따라 세 가지로 분리해 설계했다: 

① 캐릭터만 스텐실로 분리해 툰 렌더링 옵션을 제어하는 Look Dev Controller

② 기본 색보정/톤매핑과 Bloom·비네트·필름 그레인 등 언리얼 내장 포스트 프로세스, 캐릭터 툰 렌더링을 보조하는 2D Rim Light를 포함하는 기본 PostProcess

③ 뷰 최적화와 크로마키 등 방송 화면 기능을 제공하는 VV PostProcess.

 사용자 제어 요소는 C++로 구현했으며, 특히 LUT처럼 언리얼 기본 내장 기능으로 처리할 경우 사용자 커스터마이징 확장이 어려운 항목은 PP Material(Post Process Material)로 직접 구현해 확장성을 확보했다 (판단 근거는 기술적 챌린지 참고). 이를 통해 Filter 8종, 2D Rim Light 옵션 2종을 유저 제어 요소로 제공한다.



#### **- Camera**

 FOV, DOF, 타겟팅 등 카메라의 동적 요소를 중심으로 연출용 카메라 3종(standard camera, rail camera, circle camera)을 제작했다. 각 카메라의 애니메이션 요소(레일 이동, 타겟 기준 회전 이동 등)에 필요한 연산과 Ease In/Out 처리를 구현했다. 뷰포트 전환 시 자연스러운 움직임을 구현하는 데 중점을 두고 진행했다.

## 결과 (Result)

**적용 범위** : Global Light, World Control, PostProcess, Camera 시스템은 VV World의 레벨 90종(미출시 포함)에 적용되는 핵심 비주얼 시스템으로 자리잡았다.

**정량적 개선** : Global Light 프리셋 통합으로 배경당 라이팅 세팅 시간을 약 2시간에서 30분 내외로(약 75% 단축) 줄였고, 수작업 8단계였던 세팅 과정을 1단계로 통합했다. 
 PostProcess는 Filter 8종·2D Rim Light 2종, Camera는 3종(Standard/Rail/Circle)의 재사용 가능한 프리셋으로 제공된다.

**최적화** : 여러개의 Post Process Material을 하나의 구조로 통합해 관리성과 확장성을 높이고 GPU 최적화함.

**크리에이터 피드백** : Camera 시스템(Standard/Rail/Circle)의 애니메이션 자연스러움과 연출적 요소에 대해 크리에이터들의 호평을 받았다.

**아트팀/투자사 피드백** : PostProcess의 Filter(LUT)와 Bloom Profile 제공을 통해 아트팀과 투자사로부터 긍정적 평가를 받았다.
