### VV World

**목표 (Goal)**
(이 기능이 왜 필요했는지 — 문제가 아니라 앱의 목적상 필요했던 이유)

- VVWorld 앱이 정확히 어떤 서비스인지 (유저가 뭘 하는 앱인지 — 예: 아바타 커스터마이징, 가상 공간 체험 등)
VV World는 고가의 모션캡처 슈트나 전문 스튜디오 장비 없이도 언리얼 엔진 기반의 고품질 콘텐츠를 손쉽게 제작할 수 있는 버추얼 콘텐츠 제작 애플리케이션이다. 게임 엔진 지식이 전혀 없는 사용자도 언리얼 엔진 수준의 시네마틱 퀄리티로 실시간 스트리밍을 할 수 있도록 지원하는 것이 핵심 가치이며, 기존 유니티 기반 타사 툴과 차별화되는 지점이다.
- 배경/포스트프로세스/카메라가 왜 "하나로 맞아떨어져야" 했는지 — 유저 경험 관점에서 이 셋이 어긋나면 뭐가 문제였는지
약 스무명의 기존 버추얼 스트리밍 크리에이터를 대상으로 신규 서비스에 대한 요구사항을 설문 조사한 결과, 캐릭터가 매력적으로 보이는 룩뎁(50%)이 가장 높은 비중을 차지했고, 이어서 저비용 고퀄리티 모션캡처 솔루션(20%), 커스터마이징 가능한 배경(10%), 게임 스트리밍과 병행 가능한 수준의 최적화(10%) 순으로 나타났다.
이를 바탕으로, 기존 콘텐츠 제작에서 검증된 고품질 리소스를 프리셋화·최적화하여 실시간 스트리밍 환경에서도 시네마틱 퀄리티를 구현하는 것을 목표로 설정했다.
이 목표를 달성하기 위해 Global Light, World Control, Post Process, Camera 등의 기능을 신규 제작하거나 기존 기능을 개선했다.

**구현 내용 (What I Built)**
(실제로 무엇을 만들었는지, 구조 위주로 — 어떤 기술/구조를 썼는지)

- Global Light
50종 이상의 배경에 대해 언리얼 엔진 환경 라이팅을 프리셋 형태로 구성했다. Directional Light 2개(낮/밤), Sky Light, Atmosphere Sky, Exponential Fog, Volumetric Cloud, Sky Sphere Mesh, HDRI Dome을 하나의 클래스 안에서 컴포넌트로 세팅할 수 있도록 제작해, 수작업 8단계로 진행하던 세팅 과정을 1단계로 축소했다.
아뽀키 등 기존 콘텐츠 제작팀에서 사용하던 라이팅 프리셋을 최대한 그대로 계승할 수 있도록 하나의 세팅 클래스로 통합했으며, 이를 통해 배경당 약 2시간이 소요되던 작업 시간을 30분 내외로 단축했다.
툰 셰이더의 밝기에 맞춰 Exposure 등을 자동 조정해 캐릭터 라이팅과 배경이 아트적으로 조화를 이루도록 하되, 사용자가 세부적으로 커스터마이징할 수 있는 여지를 남겨두었다. "기본값만으로도 만족스러운 비주얼이 나오는 것"을 목표로 설계했다.
특히 낮/밤 시간대 변화에 따라 배경 머티리얼이 자동으로 전환되도록, 아트팀과 협의해 Material Parameter Collection(MPC) 구조로 파라미터를 전달하는 방식을 설계했다 (판단 근거는 기술적 챌린지 참고).
- World Control
아트팀이 사전 배치한 월드 내 에셋을 사용자가 직접 커스터마이징할 수 있도록, 각 에셋을 C++ 클래스로 래핑하고 공통 UInterface로 연결했다. 아트팀이 직접 세팅할 수 있도록 이 UInterface를 상속받는 Blueprint Interface를 함께 제공해, 에디터 상에서 기존 블루프린트 클래스들과도 자연스럽게 대응되도록 구성했다 (판단 근거는 기술적 챌린지 참고).
이를 통해 배경 요소별로 개별 구현을 반복하지 않고 World Control이라는 단일 시스템으로 통합 제어할 수 있도록 했다. 레벨당 최대 6개 요소를 컨트롤할 수 있으며 요소별 에셋 개수는 가변적으로 세팅 가능하다. 대형 레벨처럼 제어 대상 에셋 수가 많고 가변적인 경우, 에셋 각각의 참조를 들고 개별 호출하는 대신 MPC 전역 변수를 브로드캐스트해 다수의 에셋이 동시에 같은 상태를 반영하도록 처리했다 (판단 근거는 기술적 챌린지 참고).
- PostProcess
화면 룩을 결정하는 기능을 목적에 따라 세 가지로 분리해 설계했다: ① 캐릭터만 스텐실로 분리해 툰 렌더링 옵션을 제어하는 Look Dev Controller, ② 기본 색보정/톤매핑과 Bloom·비네트·필름 그레인 등 언리얼 내장 포스트 프로세스, 캐릭터 툰 렌더링을 보조하는 2D Rim Light를 포함하는 기본 PostProcess, ③ 뷰 최적화와 크로마키 등 방송 화면 기능을 제공하는 VV PostProcess.
사용자 제어 요소는 C++로 구현했으며, 특히 LUT처럼 언리얼 기본 내장 기능으로 처리할 경우 사용자 커스터마이징 확장이 어려운 항목은 PP Material(Post Process Material)로 직접 구현해 확장성을 확보했다 (판단 근거는 기술적 챌린지 참고). 이를 통해 Filter 8종, 2D Rim Light 옵션 2종을 유저 제어 요소로 제공한다.
- Camera
FOV, DOF, 타겟팅 등 카메라의 동적 요소를 중심으로 연출용 카메라 3종(standard camera, rail camera, circle camera)을 제작했다.
각 카메라의 애니메이션 요소(레일 이동, 타겟 기준 회전 이동 등)에 필요한 연산과 Ease In/Out 처리를 구현했다.
뷰포트 전환 시 자연스러운 움직임을 구현하는 데 중점을 두고 진행했다.

#### 1. Global Light — FLinearColor Replication 버그 (Save Scene 로드 시)

**문제상황**
Blueprint로 만들었던 클래스를 C++로 리팩토링한 뒤, Save Scene을 불러올 때 컬러 값(FLinearColor)이 일부만 반영되고 나머지는 이전 값 그대로 남는 문제가 발생했다. Save Scene 로드 과정은 `Preload → Load → Apply Preset → Post Load` 4단계로 구성돼 있고, Load 단계에서 FLinearColor 변수를 기본값(Default)으로 캐싱하는 처리를 넣었다.

**원인파악**
디버깅 결과, 다음 Apply Preset 단계가 원인이었다. 이 단계는 "Save 데이터 값과 Default 데이터 값이 같으면 다시 전송하지 않는" 최적화 로직을 갖고 있었는데, 이 비교가 구조체 전체 단위가 아니라 **구조체 안의 개별 필드(R/G/B/A) 단위**로 이루어지고 있었다. 그래서 R/G/B/A 중 하나라도 Save 값과 Default 값이 우연히 같으면 그 필드는 "변경 없음"으로 판단해 서버로 전달되지 않았고, 캐싱 이전 값이 그대로 남아 컬러가 부분적으로 틀어졌다. (`DOREPLIFETIME` 자체의 설정 문제가 아니라, 그 위에서 도는 값 비교 로직을 우회해야 하는 상황이었다.)

**해결**
서버 분기(server branch)에서만 동작하는 함수를 만들어, Apply Preset 시점에 현재 데이터를 Default 데이터로 구조체 전체 단위로 강제 재할당하도록 처리했다.

#### 2. Global Light / LookDev Controller — 캐릭터·배경 라이팅 분리 (라이트 채널)

**문제상황**
아트팀 요청으로, 배경(env)은 PBR 기반, 캐릭터는 PBR과 툰쉐이더를 혼용하는 상황에서 두 렌더링 방식 모두에서 캐릭터 라이팅(룩뎁)을 배경과 독립적으로 예쁘게 제어할 수 있어야 했다.

**원인파악**
캐릭터와 배경 라이팅이 하나의 라이트 세트를 공유하고 있어, 캐릭터 쪽만 따로 조정하면 배경도 함께 바뀌어 분리 제어가 불가능한 구조였다. 분리 방법으로 Scene Capture(별도 카메라로 렌더링 후 합성)도 검토했으나 두 가지 이유로 기각했다. 첫째, Scene Capture는 렌더링을 한 번 더 도는 구조라 비용이 크고, 이미 에디터용/방송 송출용으로 두 개를 쓰고 있어(현재 View Family 통합으로 최적화 진행 중) 여기에 하나를 더 얹기 어려웠다. 둘째, 이 작업 자체가 아트팀 요청이 컸기 때문에 아트팀이 직관적으로 다룰 수 있는 방식이어야 했는데, 복잡한 렌더 파이프라인보다는 라이트 하나에 채널 번호만 지정하면 되는 Light Channel 방식이 아트팀 입장에서 바로 납득할 수 있는 선택이었다.

**해결**
Global Light(배경)는 채널 0, VVLookDevController(캐릭터 전용 Directional Light 1개)는 채널 2로 완전히 분리하고, Sky Light처럼 GI(전역 조명)처럼 보이는 요소만 0/2 채널을 혼용해 배경과 캐릭터가 자연스럽게 어우러지도록 했다.
추가로 Forward Shading Proxy 우선순위 문제도 함께 해결해야 했다. 언리얼에서 Water, Fog 같은 일부 머티리얼은 Forward Shading 방식으로 처리되는데, 이 방식은 여러 라이트 중 우선순위(Priority)가 가장 높은 라이트 하나만 골라 연산한다. 낮/밤에 따라 활성 라이트가 서로 교체되는 구조였기 때문에, "지금 켜진 라이트가 항상 1순위가 되도록" Priority 값을 코드에서 동적으로 갱신하는 처리를 추가했다. 이 처리가 없으면 라이트가 바뀌어도 Water/Fog 같은 머티리얼은 이전 라이트 기준으로 렌더링되는 불일치가 생긴다.
`IsDay` 플래그를 MPC 파라미터로 아트팀에 노출해, 낮/밤 전환 시 배경 아트가 자동으로 반응할 수 있게 했다.

#### 3. PostProcess — 내장 기능의 커스터마이징 한계

**문제상황**
언리얼 내장 PostProcess의 LUT 등은 intensity 같은 수치 조절만 가능하고 개별 스탯을 켜고 끄는 세밀한 제어는 불가능했다. 아트팀은 기존 시네마틱 제작에서 쓰던 기능을 스트리밍 환경에서도 "정확히 그대로" 쓰고 싶어했다.

**원인파악**
내장 기능을 그대로 쓰면 커스터마이징 폭이 좁아 아트팀의 기존 워크플로우를 포기해야 하는 트레이드오프가 있었다. 초기에는 커스텀 엔진 소스에 Enable 플래그를 직접 추가하는 방식을 검토했으나 기각했다. 이유는 두 가지다. 첫째, 오픈 베타 직전이라 빌드 일정이 촉박했고, 커스텀 엔진을 수정하면 다른 개발자들의 빌드/작업 시간에도 영향이 가는 상황이었다. 둘째, 이미 PostProcess Material을 쓰는 코드 구조가 마련돼 있어서 굳이 엔진 코드를 건드릴 필요 자체가 없었다.

**해결**
언리얼 엔진 소스에서 LUT 샘플링 로직을 직접 분석해, 동일한 로직을 Material Editor에서 PP Material 함수로 그대로 재현했다. 엔진을 건드리지 않고도 아트팀이 원하는 세밀한 on/off 제어를 구현했고, 최적화를 위해 여러 기능을 각각 별도 머티리얼로 만들지 않고 하나의 PP Material 안에 함수(function) 형태로 모아 넣어 드로우콜(Draw Call) 수도 줄였다. 그 결과 Filter 8종, 2D Rim Light 옵션 2종을 유저 제어 요소로 제공할 수 있었다.

**결과 (Result)**
(완성 후 이 기능이 앱에서 어떤 역할을 하는지 — 수치가 없으면 정성적 서술도 가능)

- 적용 범위
Global Light, World Control, PostProcess, Camera 시스템은 VV World의 레벨 90종(미출시 포함)에 적용되는 핵심 비주얼 시스템으로 자리잡았다.
- 정량적 개선
Global Light 프리셋 통합으로 배경당 라이팅 세팅 시간을 약 2시간에서 30분 내외로(약 75% 단축) 줄였고, 수작업 8단계였던 세팅 과정을 1단계로 통합했다. PostProcess는 Filter 8종·2D Rim Light 2종, Camera는 3종(Standard/Rail/Circle)의 재사용 가능한 프리셋으로 제공된다.
- 최적화
PostProcess Material을 하나로 통합해 드로우콜을 줄였다. (구체적 수치는 추후 측정 후 반영 — 프로파일링 예정 항목 참고)
- 크리에이터 피드백
Camera 시스템(Standard/Rail/Circle)의 애니메이션 자연스러움과 연출적 요소에 대해 크리에이터들의 호평을 받았다.
- 아트팀/투자사 피드백
PostProcess의 Filter(LUT)와 Bloom Profile 제공을 통해 아트팀과 투자사로부터 긍정적 평가를 받았다.

아직 실측 데이터 없이 서술한 비용/구조 관련 주장 3가지. 측정 방법은 `profiling-guide.md`의 A/B 재현 절차를 따른다.

1. PostProcess 뷰 최적화 — `stat gpu`로 최적화 적용 전/후 PostProcess 항목 GPU ms 비교, 크로마키 on/off 시 `stat unit` 프레임 타임 비교
2. Global Light: MPC vs Dynamic Material Instance — 배경 10~20종 기준으로 DMI 방식을 임시 재현한 뒤 `stat scenerendering`(드로우콜/인스턴스 수), `memreport -full`(메모리)로 비교
3. World Control: 대형 레벨에서의 MPC 브로드캐스트 vs 개별 인터페이스 호출 — 이 선택의 목적은 성능 최적화가 아니라 "제어 대상 에셋 수가 많고 가변적인 대형 레벨에서, 참조를 관리하지 않고도 전역적으로 상태를 전파하기 위함"이었다. 따라서 순수 비용 비교보다는 "에셋 수가 늘어날수록 개별 호출 방식의 관리 비용(참조 유지, 호출 횟수)이 어떻게 증가하는지"를 중심으로 측정

### Sequencer Editor Tool Kits

**전체 개요**
언리얼 시퀀서 기반 콘텐츠 제작 파이프라인에서 반복되던 수작업(폴더/네이밍, 서브시퀀스 복사, 모캡 데이터 정리)을 자동화하기 위해 제작한 툴 3종. 시퀀서 생성부터 모캡 데이터 정리까지 파이프라인 전 구간의 휴먼에러와 작업 시간을 줄이는 것을 목표로 했다.

---



#### 파트 1. Sequencer Create Tool

- 문제: 신규 시퀀스를 만들 때마다 기존 템플릿을 복사해 폴더 경로와 시퀀스 이름을 수작업으로 붙여넣어야 했고, 팀 간 작업 충돌을 막기 위한 서브시퀀스도 매번 손으로 만들어야 했다. 네이밍·폴더링 규칙을 사람이 직접 맞추다 보니 휴먼에러가 잦았고, 세팅에만 30분 - 한시간 이상이 걸렸다.
- 해결: Blueprint Widget과 Python으로 생성 툴을 제작해, 프로젝트명·콘텐츠 타입·콘텐츠 코드네임(PD팀 제공)·업로드 날짜를 조합해 폴더 경로와 시퀀스 네이밍을 자동 생성하도록 했다. 팀 간 충돌 방지용 서브시퀀스를 생성 시점에 선택적으로 함께 만들 수 있게 했고, 카메라 프리셋(비율, FOV 등)과 Frame Range/FPS도 함께 설정할 수 있게 했다.
- 결과: 네이밍·폴더 프리셋 오류로 인한 휴먼에러를 약 80% 줄였고, 세팅 작업 시간을 30분 이상에서 약 5분으로 단축했다. 파이프라인에 정식 도입되어 현재까지 사용 중이다.



#### 파트 2. Mv Seq Track Tool

- 문제: 뮤직비디오처럼 메인 시퀀서의 트랙 단위로 서브시퀀스를 나눠야 하는 프로젝트에서는, 모캡 데이터를 컷 수만큼 일일이 복사하고 컷 넘버를 붙여 리네이밍하는 작업에 매번 2~3시간이 걸렸고 휴먼에러도 잦았다.
- 해결: Data Asset으로 프로젝트 경로를 지정하고 씬 넘버와 모캡 데이터를 입력하면, 필요한 서브시퀀스 수만큼 자동으로 복사·리네이밍하고 팀별로 필요한 데이터만 남기도록 정리하는 툴을 제작했다. 폴더별 컬러링 기능도 추가해 작업자 편의성을 높였다.
- 결과: 2~3시간 걸리던 작업을 1시간 내외로 단축했고 휴먼에러도 크게 줄였다. 파이프라인에 정식 안착해 사용 중이다.



#### 파트 3. Preview Takes Editor

- 문제: 시네마틱 작업 시 모캡 데이터 양이 방대해 애니메이션팀이 프리비즈용으로 필요한 데이터만 손으로 추리기엔 시간이 부족했다. 프리비즈 단계에서도 모캡 데이터 전체와 프리비즈 전용 레퍼런스 클래스·라이팅 데이터가 뒤섞여 있어 구조가 복잡했다.
- 해결: C++로 위젯 컴포넌트를 제작해 에디터에 바인딩하고, 모캡 데이터를 타입(스켈레탈 메시 등 애니메이션 데이터, 라이팅 데이터, 카메라 등)별로 캐스팅해 각 팀이 필요한 데이터만 정리해 서브시퀀스에 담을 수 있도록 했다. Mv Seq Track Tool에서 만든 서브시퀀스 리네이밍·복사·컬러링 함수를 재사용해 팀 규격에 맞춰 일관되게 처리했다.
- 결과: [진행한 컷 수 입력 예정] 규모의 컷 작업에 활용됐으며, 애니메이션팀의 프리비즈 준비 시간을 크게 단축해 프로젝트 진행에 필수적인 툴로 자리잡았다.

*(파트는 필요한 만큼 추가/삭제 가능)*

세 툴 모두 파이프라인에 정식 도입되어 현재까지 사용 중이며, 시퀀서 생성부터 모캡 데이터 정리까지 이어지는 반복 작업의 휴먼에러와 소요 시간을 전반적으로 줄였다.

### Blueprint Tool Kits

**전체 개요**
언리얼 블루프린트를 기반으로, 시네마틱 제작과 라이브 방송 송출 시 필요한 카메라/라이팅 연출 효과를 자동화한 툴킷.

---



#### 파트 1. Focus Track Tool

- 문제: 뮤직비디오 등 시네마틱 제작 시 카메라 포커스를 캐릭터 얼굴(정확히는 미간)에 지속적으로 맞춰야 했는데, 시퀀서에는 이를 자동으로 추적해주는 기능이 없어 프레임마다 포커스 값을 수동으로 조정해야 했다.
- 해결: 카메라 포커스가 타겟(캐릭터 얼굴)을 자동으로 추적하도록 하는 블루프린트 툴을 제작했다.
- 결과: 포커스 수동 조정 작업을 없애 카메라/라이팅 작업자의 반복 작업을 줄였다.



#### 파트 2. BP_FollowLight

- 문제: 라이브 방송 중 툰 렌더링 캐릭터의 얼굴이 항상 가장 예쁜 상태로 보이도록 Directional Light를 고정하고 싶었지만, 캐릭터가 움직이면 라이트 방향도 함께 따라가야 해서 수동 제어로는 대응이 불가능했다.
- 해결: 캐릭터 얼굴의 노멀 메시 방향을 타겟으로 삼아 Directional Light 방향이 자동으로 따라가도록 하는 블루프린트 툴을 제작했다.
- 결과: 캐릭터가 움직여도 방송 중 실시간으로 얼굴 라이팅이 최적 상태로 유지되도록 했다.

*(파트는 필요한 만큼 추가/삭제 가능)*

---

**종합 결과 (전체 프로젝트 관점)**
Focus Track Tool과 BP_FollowLight 모두 시네마틱 제작과 라이브 방송 각각에서 캐릭터 라이팅/카메라 품질을 자동으로 유지시켜, 수동 개입 없이도 일정 수준 이상의 비주얼 퀄리티를 보장하는 역할을 했다.
